# Scene art is pre-rendered from scripted Blender sources

This replaces the owner decision "hand-drawn 2D sprites, isometric camera" in `docs/research/rendering.md` and the "hand-drawn art" wording in ADR 0001. Characters and props are modelled and animated in Blender. Python scripts, run headlessly with `blender -b -P` and written with Claude or Codex, render them from a fixed isometric camera into sprite-sheet atlases, which the 2D Renderer (Pixi) plays. The art is not pixel art and does not copy Pixel Agents' look. The scripts fix the camera, lighting, palette, the four facing directions and the frame counts, so every character, Station and Theme looks consistent and one command rebuilds every atlas. The `.blend` sources stay rigged so that a later 3D Renderer (Three.js) can use the same models exported as glTF.

Each character gets walk, idle, one working pose per Action category, waiting, blocked and error, all in four directions. Lost and done characters fade out or leave and get no animation. The `.blend` sources live in this repo under Git LFS. The generated atlases are committed too, so building the app never needs Blender. The art is licensed CC BY 4.0, separately from the MIT code. The first illustrated Theme is office.

Everything after the `.blend` file is scripted. How a `.blend` file is made is up to whoever makes it. Every committed source must allow redistributing its raw files. For office v1, the human bases are CC0 output from MPFB2/MakeHuman, with one Agentarium rig generated by Rigify. We author every animation ourselves on that rig: AI-written keyframe scripts, polished by hand in Blender. AI-written `bpy` scripts build the props, the Stations and the room. Audited CC0 props such as Kenney's may be used. Mixamo, Quaternius assets under its QAL licence, Sketchfab downloads, and anything CC BY-SA, NC or of unclear licence are never committed (`docs/research/scene-art-pipeline.md`). Each asset carries a manifest recording its source, author, licence and changes.

The pipeline pins one exact Blender build (5.2.2 LTS to start) by version and download checksum, and refuses to run on any other. It renders with EEVEE, headless (`blender -b`), on the owner's Windows x64 machine. Blender publishes no Linux arm64 build, so the owner's aarch64 VPS cannot run it, and Cycles cannot give the toon look. The phase-3-scene 02 spike measured this (`docs/research/scene-art-pipeline.md`, section 5). A Linux x64 host could run the same scripts with EEVEE on Mesa llvmpipe under Xvfb, but that path is not measured at the pin. Changing the Blender version means rebuilding all the art.

## Considered options

- **Hand-drawn or pixel-art sprites (Aseprite).** Rejected: every extra direction or pose costs drawing time, and an AI-assisted workflow has no consistent way to keep hand drawings on one style.
- **Real-time 3D only.** Deferred rather than rejected. It costs far more per frame for tens to hundreds of characters and drops the 2D Renderer and the Pixi plan. The rigged sources keep it open.
- **Making the art by hand in the Blender UI and committing only the atlases.** Rejected: nobody could re-render after a camera or lighting change, and the look would drift between sessions.
- **Mixamo motion with private sources (split licence).** Rejected: Adobe's terms forbid sharing the raw files, so contributors could not rebuild the art and the art could not be CC BY.
- **Stylised characters with simple motion, so scripts can make all of it.** Rejected by the owner in favour of authored, natural motion. This costs more animation work.
- **A separate assets repository.** Rejected for now. It adds a sync step while there is a single Theme.
